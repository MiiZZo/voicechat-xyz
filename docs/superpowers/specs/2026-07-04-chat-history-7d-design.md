# История чата комнаты (7 дней)

**Дата:** 2026-07-04
**Область:** сервер (`apps/server/`) + общий рендерер (`apps/client/src/renderer/`)

## Цель

Сохранять историю сообщений комнаты на сервере и показывать её при входе,
чтобы участники (в т.ч. новые) видели переписку за последние 7 дней. Сейчас
сообщения ходят только p2p через LiveKit (`publishData`) и нигде не хранятся.

## Приватность (осознанная смена модели)

Раньше сервер **не видел** содержимое чата. Теперь он **хранит открытый текст
сообщений на диске 7 дней**. Это принято сознательно.

## Архитектура

**Отправка.** Клиент, как и сейчас, шлёт `publishData` (живая доставка) и
**дополнительно** POST-ит сообщение на сервер. POST-ит только отправитель —
получатели нет, поэтому дублей в истории не возникает. POST — fire-and-forget:
сбой записи в историю не мешает живой доставке.

**Хранение.** `HistoryStore` (зеркало `FileStore`) пишет в
`<HISTORY_DIR>/<roomId>.jsonl` — одна JSON-строка на сообщение (дешёвый
append). Ретеншн по `timestamp`, 7 дней; фоновая чистка переписывает файл,
отбрасывая устаревшие строки, и удаляет пустые. Кап `MAX_MESSAGES` (1000) на
комнату от разрастания (тримминг при чистке).

**Загрузка.** При входе клиент делает `GET /api/history/:roomId` → массив
записей (хронологически, ≤7 дней, кап `LOAD_LIMIT` = 200 последних). Сидит ими
список чата; живые сообщения дописываются обычным путём. Дедуп по `id`.

## Идентификатор сообщения

Вводится сквозной `id` (uuid, генерит отправитель) — общий для текстовых и
файловых сообщений, одинаковый у отправителя, получателя и в истории. Нужен
для дедупа истории и живых сообщений.

Wire-payload меняется (клиенты обновляются вместе):
```
{ type:'chat'; id; text; timestamp }
{ type:'file'; id; fileId; url; name; size; mime; timestamp }
```
(у файла раньше `id` означал fileId — теперь `id` = id сообщения, файл в
`fileId`).

Известное ограничение: identity сессии = `имя#random`, поэтому свои сообщения
из прошлой сессии не совпадут по identity и покажутся с именем и в стиле
«чужого» пузыря, а не как «ты». Для v1 приемлемо.

## Формат записи (контракт клиент↔сервер)

```ts
type HistoryRecord = {
  id: string;
  kind: 'text' | 'file';
  fromIdentity: string;
  fromName: string;
  timestamp: number;
  text?: string;                    // kind='text'
  fileId?, url?, name?, size?, mime? // kind='file'
};
```

## Изменения по файлам

**Сервер:**
- `config.ts` — `HISTORY_DIR` (`./history`), `HISTORY_TTL_DAYS` (7); bump
  `UPLOAD_TTL_HOURS` 24 → 168 (файлы живут столько же, сколько история).
- `history/history-store.ts` — `append/read/cleanupExpired/startCleanup`.
- `authorize.ts` — общий `authorizeRoom(req, config)` через
  `verifyLiveKitToken` (сейчас логика заперта в `files/routes.ts`).
- `history/routes.ts` — `POST /api/history/:roomId` (валидация zod, текст
  ≤500, совпадение комнаты) и `GET /api/history/:roomId`.
- `index.ts` — регистрация роутов + запуск чистки истории.

**Клиент (только рендерер, как `upload.ts`, без нативных команд):**
- `lib/history.ts` — `fetchHistory`, `postHistory`, тип `HistoryRecord`.
- `state/store.ts` — `pushChat` дедуп по `id`; новый `seedHistory(msgs)`
  (merge + dedup + сортировка по timestamp; живые сообщения приоритетнее).
- `components/ChatPanel.tsx` — грузит историю на входе; POST-ит при отправке
  текста и файла; сквозной `id` в wire-payload; конвертация записей в
  `ChatMessage`.

## Тестирование

Серверные тесты в стиле `smoke-upload.test.ts`:
- `HistoryStore`: append→read; ретеншн отбрасывает старьё; кап `MAX_MESSAGES`.
- Роуты: `POST` требует токен и совпадение комнаты; невалидное тело → 400;
  `GET` без токена → 401; `GET` отдаёт записи в пределах TTL и с капом.

Клиент: typecheck/lint + сборка рендерера; ручная проверка (отправить,
перезайти — сообщения на месте).

## YAGNI

Нет: редактирования/удаления сообщений, «очистить историю», сквозного
шифрования, пагинации глубже `LOAD_LIMIT`, серверного захвата через
LiveKit webhooks.
